# AI事業OS Flow Runtime

# 主戦場切替判断に関する合議用論点整理

## 1. 背景

現在、AI事業OSの Flow Engine / Runtime を開発している。

目的は、複数AIを役割分担させ、Human-in-the-loop で開発プロセスを制御すること。

主なRoleは以下。

* PM：全体判断・進行管理・承認
* Designer：仕様設計
* Reviewer：仕様・成果物レビュー
* Integrator-S：実装前の構造化・Worker Packet作成
* Worker：実装
* Debugger：実装チェック・原因調査
* Infra：実機テスト・環境確認
* Human：承認・橋渡し・外部操作

現在のFlow Runtimeは、APIチャットアプリ上でRoleごとにPromptを生成し、Humanが成果物を貼り付け、Artifactとして保存し、次StepのInputとして参照できる段階まで実装済み。

U-FLOW-01〜U-FLOW-12まで進行し、Human-in-the-loop型MVPとしては運用可能な状態に到達している。

## 3. 問題意識

今後、開発が進むと、RoleへのInputとして必要な開発物が肥大化する。

特に以下が想定される。

* アプリ本体のZIPが大容量化する
* リポジトリ全体の参照が必要になる
* 実装ファイル・差分・依存関係をAIに見せる必要が出る
* APIチャットアプリへの添付容量を超える
* 添付ベースのInput管理が破綻する

そのため、どこかの段階で **APIチャットアプリ中心の運用から、VSCode上のAIチャット中心の運用へ切り替える必要が出る可能性が高い**。

ただし、最初からVSCode中心にすると、AI事業OSの重要思想である **コンテキスト汚染の防止** が弱くなる懸念がある。

---

## 4. 現在の運用思想

AI事業OSでは、Roleを関数のように扱う。

重要なのは以下。

* Roleごとに責務を分ける
* Inputを明示する
* OutputをSchema化する
* 余計な情報を渡さない
* 上流OutputだけをInputにする
* Role間の暗黙文脈を避ける
* Human / PM がHandoffを制御する

つまり、各AIに「全部見せてよしなに判断させる」のではなく、**必要なRoleに、必要なInputだけを渡して、定義されたOutputを返させる**思想。

この思想から見ると、VSCode上でリポジトリ全体を参照できる環境は便利だが、不要なファイル・過去文脈・周辺情報を読みすぎるリスクがある。

---

## 5. 判断したい主論点

### 論点A：主戦場をいつ切り替えるべきか

候補は3つ。

#### A1. APIチャットアプリ中心を継続する

メリット。

* Flow Runtime自体の検証になる
* Role分離が明確
* Input制御しやすい
* コンテキスト汚染を抑えやすい
* Human-in-the-loop運用を磨ける

デメリット。

* 添付容量に限界がある
* リポジトリ全体参照が苦手
* 実装・差分確認が重くなる
* Integrator-S / Debugger の精度が落ちる可能性がある

#### A2. 次UnitからVSCode中心へ切り替える

メリット。

* リポジトリ参照が容易
* 実装ファイル・差分・依存関係を見やすい
* Worker / Debugger / Integrator-S の作業効率が上がる
* 添付容量問題を回避しやすい

デメリット。

* コンテキスト汚染リスクが上がる
* RoleごとのInput制御が弱くなる
* AIが不要ファイルを参照する可能性がある
* Flow Runtime自身の検証機会が減る
* PM管制塔としてのAPIチャットアプリの意義が薄くなる

#### A3. APIチャットアプリ中心を継続し、容量・参照要件で段階移行する

メリット。

* 前半はFlow Runtimeを実運用で鍛えられる
* 必要になるまでVSCode移行を遅らせられる
* コンテキスト汚染を抑えやすい
* 添付容量・参照要件が限界に来た時点で合理的に移行できる
* APIチャットとVSCodeのハイブリッド運用が可能

デメリット。

* 移行判定ルールが必要
* Handoff設計が複雑になる
* Humanの橋渡し負荷が残る
* APIチャット用とVSCode用のPacket形式を両方考える必要がある

---

## 6. PM仮説

PM仮説は **A3**。

つまり、

> APIチャットアプリを主戦場として継続しつつ、Input容量・リポジトリ参照要件・Role特性に応じて、VSCode側へ段階移行する。

最初からVSCode中心にしない。

ただし、以下のRoleはVSCode移行候補になりやすい。

* Integrator-S
* Worker
* Debugger
* Infra

理由は、リポジトリ、差分、実装ファイル、実行環境との距離が近いため。

一方、以下はAPIチャットアプリ側に残す価値が高い。

* PM
* Designer
* Reviewer
* Integrator-C

理由は、構想・判断・レビュー・制御が中心であり、全ファイル参照よりもInput制御の方が重要だから。

---

## 7. 論点B：VSCode移行時のコンテキスト汚染をどう防ぐか

VSCode側を使う場合でも、以下の制約が必要。

### 必須制約案

* 1 Unit / 1 Role / 1 Chat を原則にする
* Roleごとにチャットを分離する
* Workerには原則 Worker Packet のみ渡す
* Integrator-Sには必要Artifact一覧と対象リポジトリ参照を許可する
* Debuggerには対象差分・Acceptance Criteria・関連仕様のみ渡す
* Infraには実行手順・期待結果・環境条件のみ渡す
* PMが指定したファイル以外を根拠に判断しない
* 参照したファイル一覧をOutputに明記させる
* 不明点は推測せず AmbiguousList に出させる
* VSCode側Outputは必ずArtifactとしてAPIチャット側に戻す
* PM判断はAPIチャット側で行う

## 8. 論点C：次Unitとして何を優先すべきか

候補は以下。

### 候補1. Handoff Runtime / Migration Gate

内容。

* APIチャット内Role向けHandoff生成
* VSCode外部Role向けHandoff生成
* Role別に必要Artifact一覧を生成
* Input容量・参照要件・Role種別から移行要否を判定
* コンテキスト汚染防止ルールをHandoffに埋め込む
* 外部Roleから戻ってきたOutputをArtifactとして取り込む

狙い。

* APIチャット中心運用とVSCode外部運用を接続する
* 主戦場切替を感覚ではなくルールで判断する
* Humanの橋渡しミスを減らす

### 候補2. Runtime Log / Trace

内容。

* 誰に何を渡したか
* どのArtifactをInputにしたか
* どのRoleが何を返したか
* どの判断で次Stepに進んだか
* 差戻し理由
* 承認履歴

狙い。

* Flowの監査性を高める
* あとから判断経路を追える
* コンテキスト外でも履歴復元しやすくする

### 候補3. Output Schema Validation

内容。

* Role OutputがSchemaに合っているか検証
* 必須項目不足の検出
* 命名規則違反の検出
* Output種別の誤判定防止

狙い。

* 保存Artifactの品質を上げる
* 次Step Inputの破綻を減らす

### 候補4. Review Gate Extension

内容。

* PMDecision
* Integrator-S Packet
* Infra TestPlan
* ReworkInstruction

など、従来Reviewが入りにくい重要Outputに軽量Review Gateを追加する。

狙い。

* 重要判断の品質を上げる
* PM単独判断の見落としを減らす

## 10. PM仮決定案

PMの仮決定は以下。

### 主戦場方針

**A3：APIチャット中心を継続し、容量・参照要件でVSCodeへ段階移行**

### 次Unit

**U-FLOW-13: Handoff Runtime / Migration Gate**

### 目的

APIチャットアプリ内Role運用と、VSCode外部Role運用の両方に対応するHandoff生成機能を作る。

### U-FLOW-13で扱うべき機能

* Role別Handoff Packet生成
* 必要Artifact一覧生成
* Input容量・参照要件の判定
* APIチャット内実行 / VSCode外部実行の推奨判定
* VSCode外部実行時のコンテキスト汚染防止ルール付与
* 戻りOutputの受領条件定義
* 保存先Artifact種別の提案
* PM承認後に次Stepへ進める
